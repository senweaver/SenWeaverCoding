# 编码模式 — 十二种编程工作流

> **SenWeaverCoding (sen)** — 完全基于 Rust 构建的自主 AI 智能体运行时与 CLI 代码编辑器。

本文档描述了 `sen` 中可切换的十二种编程模式。每种模式配置了不同的行为特征：系统提示注入、工具白名单、审批策略、工具后置钩子和自动验证行为。

在 REPL 中使用 `/mode <名称>` 或 `/m <名称>` 切换模式（例如 `/m tdd`、`/m harness`）。模式可在会话中随时切换。

---

## 快速参考

| 模式 | 别名 | 类型 | 审批 | 自动验证 |
|------|------|------|------|----------|
| **Vibe** | `v` | 完全自主 | 默认 | 否 |
| **Agent** | `ag`, `auto`, `agentic` | 全自主编排器 | 自动批准 | 是 |
| **Spec** | `s` | 规范驱动 | 默认 | 是 |
| **Plan** | `p` | 只读规划 | 只读 | 否 |
| **Ask** | `a`, `q` | 只读问答 | 只读 | 否 |
| **TDD** | `t` | 测试驱动开发 | 默认 | 是 |
| **Debug** | `d`, `dbg` | 系统化调试 | 默认 | 是 |
| **Architect** | `arch`, `design` | 架构与审查 | 默认 | 否 |
| **Pair** | `pp`, `collab` | 结对编程 | 默认 | 检查点 |
| **ContextEng** | `ce` | 上下文工程 | 默认 | 是 |
| **MVAI** | `mvai` | 接口架构 | 默认 | 是 |
| **Harness** | `hn`, `hs` | 工程级工作流 | 自动批准 | 是 |

## 第一部分 — 前八种模式

### 1. Ask 模式 (`ask`, `a`, `q`)

**类型：** 只读问答

**审批策略：** 只读 — 所有写操作在工具过滤层被阻止。

**工具：** 仅限文件读取、搜索和网络工具。`todo_write` 和 `update_plan` 被排除。

**描述：**

Ask 模式是理解陌生代码最安全的模式。智能体读取文件、搜索代码库、执行网络搜索并解释发现的内容 — 但不进行任何文件修改，也不执行任何有副作用的 shell 调用。

适用场景：

- 了解新代码库的架构
- 解释特定模块的功能
- 追踪复杂系统中的数据流
- 在确定方案之前研究某个库或 API

智能体专注于以代码引用为支撑的清晰解释，引用精确的文件路径和行号。

**使用时机：**

```
sen  --mode ask
/m ask
```

当你需要答案而非变更时，使用 Ask 模式。

---

### 2. Plan 模式 (`plan`, `p`)

**类型：** 只读规划与分析

**审批策略：** 只读

**工具：** 所有读取工具 + `todo_write` 和 `update_plan`。不允许文件写入和 shell。

**描述：**

Plan 模式在 Ask 的基础上增加了任务管理能力。智能体可以创建结构化计划、将工作分解为有序步骤并评估风险 — 但仍然不进行任何文件修改。

这是用于架构讨论、功能设计会议和影响分析的模式。智能体将：

1. 映射所有受提议变更影响的文件
2. 将工作分解为可独立验证的步骤
3. 识别步骤间的依赖关系和外部需求
4. 为每个步骤指定验证命令
5. 标记风险和破坏性变更的关注点

**Plan → Spec：自然的递进流程**

规划完成后，你可以批准计划并切换到 Spec 模式执行：

```
/m plan
> 设计一个为 API 添加 OAuth2 认证的计划
[智能体生成详细计划]

/m spec
> 执行我们刚刚创建的 OAuth2 认证计划
[智能体逐步执行计划并进行验证]
```

**Plan → Spec 流水线** 是复杂任务的推荐工作流：

```
Plan（只读）──[用户批准]──▶ Spec（结构化执行）──▶ 验证
     ↑                                    │
     └────────[反馈 / 修订]────────────────┘
```

由于 Plan 模式只读，你可以在 Plan 和任何其他模式之间自由切换。先规划工作，再用适当的执行模式来实施。

**使用时机：**

```
sen  --mode plan
/m plan
```

最适合：架构讨论、功能设计、了解影响范围以及在编码之前创建可执行计划。

### 3. TDD 模式 (`tdd`, `t`)

**类型：** 带有周期跟踪的测试驱动开发

**审批策略：** 默认（有监督）

**自动验证：** 是 — 每次文件写入/编辑后自动运行测试套件。

**工具后置行为：** `AutoVerify`

**描述：**

TDD 模式严格执行红-绿-重构纪律。智能体必须按顺序遵循循环：

1. **红** — 编写描述期望行为的失败测试。运行测试套件并确认测试按预期失败。
2. **绿** — 编写使失败测试通过的最少代码。不添加额外功能。运行所有测试并确认通过。
3. **重构** — 在保持所有测试通过的同时清理实现。每次重构步骤后运行测试。

智能体使用 `incremental_optimize` 跟踪每个 TDD 周期：在周期开始时设置检查点，跟踪红色阶段，跟踪绿色阶段，跟踪重构阶段，并生成最终周期报告。

**规则：**

- 没有失败测试就不要编写实现代码
- 每个测试对应一个行为 — 保持测试的聚焦和描述性
- 每个周期后运行完整测试套件，不仅仅是新测试
- 如果在实现过程中发现 bug，先编写回归测试

**使用时机：**

```
sen  --mode tdd
/m tdd
```

最适合：为现有测试套件添加新功能、构建具有明确契约的模块，或者当你希望对正确性有最大信心时。

---

### 4. Debug 模式 (`debug`, `d`)

**类型：** 四阶段协议的系统化调试

**审批策略：** 默认

**自动验证：** 是

**工具后置行为：** `AutoVerify`

**描述：**

Debug 模式应用严谨的四阶段根因分析。智能体**禁止直接跳到修复** — 必须遵循协议：

**阶段 1 — 复现：** 运行失败的命令/测试并捕获确切的错误输出。识别失败的断言、异常或意外行为。

**阶段 2 — 假设：** 形成最多 3 个关于根因的排序假设。根据错误消息、堆栈跟踪和最近变更按可能性排序。

**阶段 3 — 隔离：** 对每个假设（从最可能的开始），添加诊断输出来缩小原因范围。在做出变更前收集证据。

**阶段 4 — 修复与验证：** 应用最小修复，运行原始失败命令，确认通过。然后运行完整测试套件检查回归。修复后移除诊断代码。

**规则：**

- 不要猜测然后检查 — 先收集证据
- 不要同时应用多个修复；一次只改一件事
- 始终验证修复解决了原始问题并通过了回归测试
- bug 修复后移除诊断代码

**使用时机：**

```
sen  --mode debug
/m debug
```

最适合：神秘 bug、间歇性故障以及之前修复尝试失败的任何情况。

---

### 5. Architect 模式 (`architect`, `arch`)

**类型：** 高层设计与代码审查，配合针对性编辑

**审批策略：** 默认

**工具：** 读取工具 + 针对性写入工具（`file_write`、`file_edit`、`multi_edit`）+ `diagnostics` + `shell` + `git_operations` + `code_to_spec` + `incremental_optimize`。

**描述：**

Architect 模式用于高层设计和技术决策。智能体广泛阅读，分析架构和依赖关系，识别技术债务，并进行针对性的结构编辑 — 但关注全局而非实现细节。

**职责：**

1. 分析代码库结构、依赖关系和架构模式
2. 识别技术债务、设计缺陷和改进机会
3. 在组件/模块层面设计具有清晰接口的解决方案
4. 审查现有代码的正确性、安全性和可维护性
5. 记录架构决策及其理由

**工作流：**

- 从阅读项目结构开始（Cargo.toml、mod.rs 文件、关键入口点）
- 在提出变更建议之前映射模块依赖和数据流
- 提出变更时需指定：受影响的文件、新的接口/trait、迁移路径和测试策略
- 优先重构现有抽象而非引入新的抽象
- 明确标记破坏性变更并提出向后兼容的替代方案

**约束：**

- 关注做什么和为什么，而非详细的如何做（将实现留给 Agent/Vibe/Spec 模式）
- 限制编辑范围：接口定义、模块结构、配置和文档
- 始终考虑：性能影响、向后兼容性、安全面

**使用时机：**

```
sen  --mode architect
/m architect
```

最适合：项目重构、引入新子系统、架构审查和技术债务评估。

---

### 6. Pair 模式 (`pair`, `pp`)

**类型：** 交互式协作结对编程

**审批策略：** 默认

**工具后置行为：** `Checkpoint` — 智能体在每批操作后暂停并提示用户确认后再继续。

**描述：**

Pair 模式将智能体变成一个协作编程伙伴。智能体会出声思考，逐一提出变更建议，并在继续之前频繁确认。

**工作流：**

1. **讨论** — 在编写代码之前分享思维模型和方法
2. **提议** — 解释你要做什么以及为什么
3. **实现** — 在隐式或显式达成一致之后
4. **共同验证** — 与用户一起运行测试并审查输出
5. **迭代** — 请求反馈，根据需要调整方向

**沟通风格：**

- 出声思考 — 随时解释推理过程
- 发现潜在问题时立即提出
- 存在权衡时提供替代方案
- 在自然断点处询问"这样看起来对吗？"
- 如果用户安静，主动建议下一步

**检查点行为：** 每次有意义的变更后，智能体会暂停等待用户确认。用户可以批准、要求修改或完全转变对话方向。

**使用时机：**

```
sen  --mode pair
/m pair
```

最适合：接触新代码库、教学、设计讨论、代码审查，以及你想要对每个变更有完全可见性和控制权的场景。

---

### 7. ContextEng 模式 (`context`, `ce`)

**类型：** 上下文工程 — 先探索后精准出击，适用于大型代码库

**审批策略：** 默认

**自动验证：** 是

**工具后置行为：** `ImpactAnalysis` — 每批操作后，智能体分析并报告上下文变化和影响范围。

**描述：**

ContextEng 模式专为在上下文管理是主要挑战的大型复杂代码库中工作而设计。它强制执行一个必须按顺序完成的四阶段协议 — 在了解地形之前不编写代码。

**阶段 1 — 探索（任何写操作前必须完成）：**

1. 确定任务范围：识别用户需求并列出可能受影响的子系统
2. 使用 `code_to_spec` 快速分析
3. 先搜索再读取：使用 `content_search` 和 `glob_search` 定位相关代码。**永远不要**对整个文件直接使用 `file_read`
4. 精准读取：定位后只读取相关行范围
5. 不读取过期内容：如果本次会话中修改了文件，在引用之前重新读取

**阶段 2 — 映射（依赖与影响分析）：**

6. 构建上下文映射：要修改的文件、依赖这些文件的文件（爆炸半径）、覆盖受影响代码的测试文件
7. 报告映射：向用户展示结构化摘要
8. 预算检查：确认上下文预算能够容纳剩余工作

**阶段 3 — 精准出击（精确且经过验证的编辑）：**

9. 一次只关注一件事：进行实现目标的最小编辑
10. 立即验证：每次编辑后运行检查/测试命令
11. 编辑后重新读取：修改文件后如果需要再次使用其内容，重新读取当前状态

**阶段 4 — 巩固：**

12. 影响报告：总结已变更的文件、已验证的依赖、已消耗的上下文预算
13. 持久化记忆：在 `memory_store` 中存储关键决策和架构上下文

**工具纪律：**

- 首选调用顺序：`content_search` → `glob_search` → `file_read`（精准）→ `file_edit` → 验证
- **永远不要**在未先缩小到具体行范围的情况下 `file_read` 超过 500 行的文件
- 探索多个文件时将并行读取批量放入单个工具调用组
- 在重新读取可能已在会话记忆中的文件之前使用 `memory_recall`

**反模式（强制执行）：**

- 未经事先搜索就读取整个大文件 — 被阻止
- 未完成映射阶段就编辑代码 — 被阻止
- 忽略上下文预算警告 — 必须在继续之前总结/丢弃
- 在一次工具调用中进行多个无关编辑 — 拆分它们

**使用时机：**

```
sen  --mode context
/m context
```

最适合：大型生产代码库、不熟悉的领域、触及多个文件的复杂重构。

### 8. MVAI 模式 (`mvai`)

**类型：** 模型-视图-智能体-接口 — 接口优先、可观测、可测试的架构

**审批策略：** 默认

**自动验证：** 是

**描述：**

MVAI 模式将模型-视图-智能体-接口架构模式应用于智能体驱动的开发。通过在每一层强制执行清晰的关注点分离，确保系统的可靠性、可观测性和可测试性。

**架构层：**

1. **模型（Model）** — 数据结构和业务逻辑。在实现之前定义清晰的类型和接口。
2. **视图（View）** — 面向用户的输出和展示。保持展示逻辑与业务逻辑分离。
3. **智能体（Agent）** — 决定采取什么行动的编排层。在每个决策点记录推理过程。
4. **接口（Interface）** — 层间契约。在边界处定义显式接口（trait、类型、schema）。

**开发规则：**

- **接口优先**：在编写实现之前定义 trait/接口。
- **可观测的决策**：在每个重大操作之前说明原因，创建审计跟踪。
- **验证非确定性**：将 LLM 生成的内容视为不可信的，在据此行动之前根据 schema/类型验证输出。
- **在边界处测试**：在接口边界编写测试，而非实现细节。

**架构决策追踪：**

智能体使用 `incremental_optimize` 追踪所有重大架构决策：设置检查点、追踪接口定义、获取质量建议、生成最终架构报告。

**质量检查清单：**

- 每个新模块都有定义的接口
- 每个智能体决策都有推理日志
- 每个外部交互都有错误处理
- 非确定性输出在使用前经过验证

**使用时机：**

```
sen  --mode mvai
/m mvai
```

最适合：构建健壮的智能体系统、设计多层架构、创建可测试的智能体工作流。

## 第二部分 — 四种高级模式（详细）

以下四种模式代表了逐步更加结构化的工程工作流。**Vibe** 和 **Agent** 是两种完全自主模式，结构化程度不同。**Spec** 添加了基于 OpenSpec 的规范优先纪律和技能编排。**Harness** 将所有工程最佳实践组合为一个内聚的六层协议。

---

### 9. Vibe 模式 (`vibe`, `v`)

**类型：** 完全自主 — 快速原型和自由编码

**审批策略：** 默认（有监督）

**默认模式：** 当 `sen` 启动时未指定显式 `--mode` 参数时，Vibe 是默认模式。

**工具：** 所有工具 — 无限制。

**描述：**

Vibe 模式给予智能体完全的工具访问权限和最少的提示。自主工作，快速行动，只在需求真正模糊时才询问人类。这是默认模式，因为大多数编码会话从探索性、低风险的工作开始 — 而 Vibe 的零开销使其成为从想法到原型的最快路径。

**核心理念：**

Vibe 模式体现了**心流状态**原则：减少摩擦，信任智能体，让它全速运行。智能体拥有所有 130+ 个工具，可以读写任何文件，执行任何 shell 命令，并独立做出决策。

**使用时机：**

- 快速原型和实验
- 需求清晰的一次性任务
- 目标尚未完全定义的探索性编码
- 当你只想让智能体"直接做"而不需要仪式感时

**不适用场景：**

- 具有依赖关系的复杂多文件变更（使用 **Agent** 或 **Spec**）
- 需要根因分析的 bug 修复（使用 **Debug**）
- 向经过测试的代码库添加功能（使用 **TDD**）
- 上下文管理至关重要的大型代码库（使用 **ContextEng**）
- 需要检查点和验证的工程级工作流（使用 **Harness**）

**纪律：**

尽管是最自由的模式，Vibe 模式仍然在系统提示中注入了**验证纪律**。智能体绝不能在没有展示通过的命令输出的情况下声称修复已完成。所有模式都强制执行"证据先于断言"。

**示例会话：**

```
sen 
> 为 API 客户端添加速率限制器
> 使其可通过环境变量配置
> 为速率限制逻辑编写测试
> 运行完整测试套件
```

智能体将自主地完成这个序列，读取文件、编写代码、运行测试并自我修正 — 不需要在每一步都请求许可。

**快捷方式：** 由于 Vibe 是默认模式，你很少需要显式切换到它。直接启动 `sen` 并开始工作即可。

---

### 10. Agent 模式 (`agent`, `ag`, `auto`, `agentic`)

**类型：** 全自主编排器 — 分解、执行、验证、综合

**审批策略：** 自动批准 — 所有操作自动通过。执行过程中无交互式提示。

**自动验证：** 是

**描述：**

Agent 模式是最强大的自主模式。它将完全的工具访问与自动批准和三阶段执行协议相结合：分析/分解 → 执行/自我修正 → 综合/验证。智能体既是执行者也是编排者 — 它将复杂任务分解为子任务，通过质量门控执行，在失败时自我修正，并综合最终结果。

与 Vibe 模式（快速且非结构化）和 Spec 模式（遵循你创建的规范）不同，Agent 模式为复杂任务创建自己的执行计划并自主驱动完成。

**阶段 1 — 分析与分解：**

1. **分析**任务后再行动。阅读相关文件，理解代码库结构，识别所有受影响的组件。
2. **分解**任务为独立的、可验证的子任务。每个子任务应有清晰的输入、输出和成功标准。
3. **通过 `todo_write` 规划**：对于涉及 3 个以上文件的任务，将每个子任务注册为待办事项。包括：受影响的文件、预期变更和验证命令。

**阶段 2 — 执行：**

4. **执行**子任务按依赖顺序。对于每个子任务：读取上下文，实现，验证编译/通过，然后标记完成。
5. **自我修正** — 如果变更后构建/测试失败，立即使用系统化调试协议诊断和修复。不留下破损状态。
6. **逐步验证** — 每个子任务完成后，运行相关检查命令并确认成功后再进入下一个。

**阶段 3 — 综合与验证：**

7. **综合** — 所有子任务完成后，审查聚合结果。它是否满足原始需求？运行完整的构建 + 测试套件。
8. **自我评估** — 将输出与原始规范对比。如果存在差距，创建后续子任务而非内联修补。
9. **报告**最终状态，附上所有已做变更的摘要。

**自主规则：**

- 独立做出决策。除非需求真正模糊（多种有效解释），否则不要向用户请求澄清。
- 当存在多种方法时，选择满足需求的最简单方法。
- 承诺在一次会话中完成整个任务。不留下半成品。

**编排纪律：**

- 每个子任务必须可独立验证（可以运行自己的测试/检查）。
- 最小化跨子任务依赖；不可避免时记录它们。
- 使用 `content_search` / `glob_search` 在规划前发现所有受影响的文件。
- 当子任务验证失败时，先隔离调试再继续。
- 如果子任务需要研究（如 API 文档），主动使用网络搜索工具。
- 根据需要毫不犹豫地使用 `shell` 进行构建/测试/git 操作。

**质量门控：**

- 没有通过验证命令的子任务不算完成。
- 最终综合步骤必须运行完整的项目构建 + 测试套件。
- 如果总变更超过 10 个文件，创建所有修改的摘要。

**大型任务的规范纪律：**

对于涉及 5 个以上文件的任务，Agent 模式也纳入规范优先纪律：

1. 首先运行 `code_to_spec(action="summarize", paths=["."])` 了解代码库
2. 运行 `code_to_spec(action="analyze", paths=["./src"])` 映射依赖结构
3. 使用 `code_to_spec(action="generate", paths=["."], title="<task>", description="<desc>")` 创建 SPEC.md
4. 使用 `incremental_optimize(action="checkpoint", description="Agent: <phase> started")` 在阶段边界
5. 每个实现批次后使用 `incremental_optimize(action="suggest")` 获取优化提示
6. 最终综合：`incremental_optimize(action="report", description="Agent Task Complete: <name>")`

**使用时机：**

```
sen  --mode agent
/m agent
```

最适合：复杂的多步骤任务，你希望智能体拥有完整的执行权，自动批准批量操作，并交付完整结果而无需中途确认。

**Agent 与 Vibe 对比：**

| 方面 | Vibe | Agent |
|------|------|-------|
| 审批 | 默认（有监督） | 自动批准 |
| 任务分解 | 无 | 3+ 文件任务强制 |
| 自我修正 | 可选 | 失败时必须 |
| 质量门控 | 无 | 逐子任务 + 最终 |
| 规划 | 即兴 | 结构化 (todo_write) |
| 规范创建 | 否 | 是 (5+ 文件任务) |
| 最适合 | 快速任务 | 复杂多步骤任务 |

### 11. Spec 模式 (`spec`, `s`) — 基于 OpenSpec + 超能力的规范驱动

**类型：** 具有增量优化和工程技能的规范驱动开发

**审批策略：** 默认

**自动验证：** 是

**工具：** 所有读取工具 + 写入工具 + `shell` + `git_operations` + `diagnostics` + `todo_write` + `update_plan` + `memory_store` + `memory_search` + `code_to_spec` + `incremental_optimize`。

**描述：**

Spec 模式是规划与执行之间的桥梁。它建立在 **OpenSpec**（构建之前先达成一致）和**超能力**（工程技能作为默认行为）之上，将结构化规范与主动的工程纪律相结合。它吸收了 Plan 模式的结构化思维，并添加了正确执行的纪律：编码前创建 SPEC.md，主动使用工程技能，验证每一步能够编译，使用 `incremental_optimize` 追踪所有变更，并在宣布完成前运行完整的测试套件。

**三步规范工作流：**

**步骤 1 — 分析与规范（OpenSpec：构建之前先达成一致）：**

在任何代码变更之前，使用 `code_to_spec` 了解现有代码库：

- 运行 `code_to_spec(action="summarize", paths=["."])` 获取代码库结构的快速概览
- 运行 `code_to_spec(action="analyze", paths=["./src"])` 从相关目录提取结构信息
- 运行 `code_to_spec(action="generate", paths=["./src"], title="<title>", description="<desc>")` 创建 SPEC.md
- 修改现有代码前，运行 `code_to_spec(action="compare", spec_path="SPEC.md")` 检查规范与现实之间的差距

**步骤 2 — 追踪与优化（增量改进）：**

使用 `incremental_optimize` 系统化地管理变更：

- `incremental_optimize(action="checkpoint", description="pre-change snapshot")` — 开始前设置快照
- `incremental_optimize(action="track", file="<path>", change_type="modified", summary="<desc>", lines_added=N, lines_removed=M)` — 追踪每次变更
- `incremental_optimize(action="suggest")` — 获取优化建议
- `incremental_optimize(action="verify", change_id=N, suggestion_id="<id>")` — 标记已应用的改进
- `incremental_optimize(action="report", description="<title>")` — 总结优化循环

**步骤 3 — 执行与验证（标准规范驱动工作流）：**

1. 与用户澄清需求和边缘情况
2. 使用 `todo_write` 创建包含文件级变更的详细计划
3. 逐步执行计划，用构建/测试命令验证每一步
4. 完成所有步骤后，运行完整测试套件并报告结果

**工程技能（超能力 — 无需被告知即主动使用）：**

Spec 模式将以下工程技能注入为默认行为：

- **头脑风暴**：在选择方法前探索替代方案。面对非平凡的设计决策时使用头脑风暴技能。
- **规划**：将工作分解为有序的、可独立验证的步骤。对每个多步骤任务使用 `todo_write`。
- **TDD**：先编写失败测试，然后实现，然后重构。对所有新功能使用 TDD 循环。
- **调试**：复现 → 假设 → 隔离 → 修复。调试时绝不猜测。
- **代码审查**：正确性、安全性、测试、性能、可读性。对所有变更使用审查清单。
- **Git 工作树**：在工作树中隔离实验。绝不用冒险实验污染主工作目录。

**硬性规则：**

- **在进行重大代码变更之前必须创建 SPEC.md**
- **必须验证每一步能够编译后再进入下一步**
- **对于任何非平凡的修改，必须使用 `incremental_optimize` 追踪变更**

**规划与规范纪律（继承自 `planning_rules`）：**

- **文件映射**：从列出所有将被创建、修改或删除的文件开始
- **步骤分解**：将工作分解为有序的、可执行的步骤。每步应可独立验证
- **依赖关系**：识别步骤间依赖和外部需求
- **测试策略**：为每个步骤指定验证方法（测试命令、预期输出、手动检查）
- **风险评估**：标记任何可能破坏现有功能的步骤并描述缓解措施

**为什么选择 Spec 而非 Vibe：**

Vibe 快速且无约束。Spec 增加了开销 — 但这些开销在以下情况下是值得的：

- 任务涉及 3 个以上有相互依赖的文件
- 变更有可以验证的清晰规范
- 你需要变更内容和原因的审计跟踪
- 你希望工程技能（TDD、头脑风暴等）自动触发

**为什么选择 Spec 而非 Harness：**

Harness 是最结构化的模式（六层、自动批准、技能编排、智能体团队协调）。Spec 为你提供 OpenSpec 纪律、超能力技能自动化和变更追踪，而没有 Harness 的全部开销。对于大多数实际任务，Spec 是合适的平衡点。

**Plan → Spec：自然的递进流程：**

```
/m plan
> 设计一个为 API 网关添加 OAuth2 认证的计划

[Plan 产出：文件映射 → 步骤分解 → 依赖关系 → 测试策略 → 风险评估]
[用户审查并批准计划]

/m spec
> 执行我们刚刚创建的 OAuth2 认证计划

[Spec 创建 SPEC.md → 使用 incremental_optimize 追踪变更 → 逐步
 执行 → 验证每一步 → 运行完整测试套件 → 报告结果]
```

由于 Plan 模式只读，你可以在 Plan 和 Spec 之间自由切换。先用 Plan 规划工作，然后用 Spec 模式执行。

**示例：**

```
sen  --mode spec
> 为网关模块添加具有重试逻辑的 webhook 投递系统
```

智能体将：

1. **OpenSpec**：创建 SPEC.md 记录 webhook 投递契约、重试策略、失败处理和验收标准
2. **超能力**：对缓存策略使用头脑风暴，对核心算法使用 TDD，对任务分解使用规划
3. **追踪**：设置变更前快照的检查点
4. **执行**：将工作分解为：定义 webhook 结构体 → 实现投递队列 → 添加重试逻辑 → 添加测试 → 验证
5. **验证**：执行每一步，每步后运行构建/测试
6. **报告**：使用 `incremental_optimize` 追踪每次变更并运行完整测试套件

### 12. Harness 模式 (`harness`, `hn`, `hs`) — 工程级工作流

**类型：** 工程级工作台 — 规范 → 技能编排 → 会话检查点 → 验证

**审批策略：** 自动批准 — 所有操作自动通过。执行过程中无交互式提示。

**自动验证：** 是

**工具后置行为：** `AutoVerify`

**工具：** 所有 spec_tools + `skill_tool` + `skill_http` + `read_skill` + `enter_plan_mode` + `exit_plan_mode` + `agent_delegate` + `agent_summary` + `agent_compact`。

**描述：**

Harness 模式是 `sen` 中最先进、最结构化的模式。它将六种工程方法论的最佳实践 — **OpenSpec**、**Superpowers**、**GSD**、**OMC**、**ECC** 和 **Trellis** — 组合为一个内聚的六层协议。每个任务按顺序流经所有六层，自动批准实现不间断执行。

Harness 专为质量、可追溯性和系统纪律不可妥协的工程级工作流设计。适用场景：

- 任务是关键性的或面向生产的
- 多个工程师或智能体需要协作
- 代码库具有复杂的相互依赖
- 你需要从规范到验证的完整审计跟踪
- 你希望从会话中提取可复用的技能和模式

**六层协议：**

---

#### 第 1 层 — 规范层（OpenSpec：构建之前先达成一致）

**目的：** 在编写任何代码之前定义你要构建什么。

1. **澄清需求** — 识别确切的输入、输出和边缘情况
2. **编写结构化规范** — 提案 → 规格 → 设计 → 任务结构
3. **与用户对齐** — 在继续之前确认理解
4. **记录验收标准** — 你如何知道任务完成了？

**规则：**

- 在完成规范对齐步骤之前永远不要开始编码
- 如果需求模糊，请用户澄清 — 不要猜测
- 将规范写入 `.senweavercoding/plans/` 或 `STATE.md` 以确保可追溯
- 规范是活文档：需求变更时更新它们

**OpenSpec 原则：** 软件中最昂贵的错误是构建错误的东西。OpenSpec 在智能体和用户之间执行一个契约：构建之前先达成一致。

---

#### 第 2 层 — 技能编排层（Superpowers：工程纪律作为默认行为）

**目的：** 主动使用工程技能。让它们成为你的默认行为。

**内置工程技能（无需被告知即使用）：**

- **头脑风暴** — 在选择方法前探索替代方案。面对非平凡设计决策时使用头脑风暴技能。
- **规划** — 将工作分解为有序的、可独立验证的步骤。对每个多步骤任务使用 `todo_write`。
- **TDD** — 先编写失败测试，然后实现，然后重构。对所有新功能使用 TDD 循环。
- **调试** — 复现 → 假设 → 隔离 → 修复。调试时绝不猜测。
- **代码审查** — 正确性、安全性、测试、性能、可读性。对所有变更使用审查清单。
- **Git 工作树** — 在工作树中隔离实验。绝不用冒险实验污染主工作目录。
- **子智能体驱动开发** — 将复杂任务分解为并行子任务并分配给专门的智能体。

**规则：**

- 当存在相关的技能目录时，使用 `read_skill` 加载技能上下文
- 使用 `todo_write` 注册每个子任务及预期变更和验证命令
- 当任务涉及 3 个以上文件时，先分解为子任务
- 对于有风险的实验优先使用 git 工作树

---

#### 第 3 层 — 会话管理层（GSD：解决上下文腐化）

**目的：** 防止长任务中上下文退化。跨会话边界维护状态。

1. **频繁设置检查点** — 每个逻辑阶段后创建会话检查点
2. **保持上下文整洁** — 将相关的工具调用批量处理。避免混合无关变更
3. **使用结构化状态文件** — 为长任务维护 `STATE.md`、`ROADMAP.md`、`TASKS.md`
4. **退化前整合** — 如果上下文超过 50%，总结并丢弃过期历史
5. **原子提交** — 每个会话阶段应产生一个干净的、可回滚的提交

**状态文件纪律：**

- `STATE.md` — 当前状态、阻塞项、下一步行动
- `ROADMAP.md` — 带有已完成/进行中/待办标记的总体计划
- `TASKS.md` — 带有勾选标记的逐文件任务清单
- 每个会话检查点后：更新所有三个文件

**GSD 原则：** 上下文腐化是长时间运行任务的敌人。每消耗 30-50% 的上下文，停下来整合。目标是在会话的任何时间点，你都可以仅从结构化制品恢复 — 而非从聊天历史。

---

#### 第 4 层 — 智能体团队编排层（OMC：团队优先执行）

**目的：** 当并行执行有益时，跨智能体编排子任务，配备监督者。

1. **识别独立子任务** — 没有共享状态或顺序依赖的任务
2. **为每个子任务分配智能体** — 使用 `sessions_send` 或并行工具调用
3. **用监督者智能体协调** — 监督者审查所有输出，合并，解决冲突
4. **综合最终结果** — 根据原始规范审查聚合输出

**规则：**

- 仅并行化真正独立的子任务 — 不要并行化依赖步骤
- 每个子智能体在返回结果前必须为其工作设置检查点
- 监督者智能体在综合前必须验证所有子智能体输出能够编译/通过
- 如果子智能体失败，先隔离诊断失败后再重试

**OMC 原则：** 完成大型任务的最快方式是找到其中的并行性。不是所有任务都可以并行化 — 但许多看起来是顺序的任务实际上有独立的阶段。

---

#### 第 5 层 — 能力增强层（ECC：技能、记忆、安全、验证）

**目的：** 工程化工作台本身 — 提取模式、持久化知识并强制执行质量门控。

1. **技能和直觉** — 从完成的任务中提取可复用的模式到技能文件中。下次遇到类似任务时，技能应自动触发。
2. **持久化记忆** — 使用 `memory_store` 保存关键决策、架构上下文和经验教训。未来会话应受益于本次会话的发现。
3. **安全扫描** — 验证每次变更中没有密钥、没有路径遍历、没有注入漏洞。
4. **验证循环** — 每次变更必须通过构建 → lint → 测试 → 安全检查。

**每次代码变更的验证序列：**

1. `cargo check` 或等效命令 — 能否编译？
2. `cargo clippy` 或等效命令 — 是否通过 lint？
3. `cargo test` 或等效命令 — 所有测试是否通过？
4. 安全检查 — 没有硬编码密钥，没有不安全的模式

**ECC 原则：** 每个完成的任务都是改进系统本身的机会 — 通过可复用的技能、持久化的记忆和强制执行的质量标准。

---

#### 第 6 层 — 结构与项目记忆层（Trellis：规范、任务、工作空间）

**目的：** 围绕结构化制品组织工作，而非聊天历史。实现团队延续性和会话恢复。

**核心结构：**

- `.senweavercoding/plans/*.md` 或 `.trellis/spec/` — 需求和设计规范
- `.senweavercoding/plans/*.md` 或 `.trellis/tasks/` — 逐任务上下文和状态
- `.senweavercoding/plans/*.md` 或 `.trellis/workspace/` — 会话日志和延续性

**项目记忆纪律：**

- 每个主要阶段后将架构决策存储在 `memory_store` 中
- 开始新会话前使用 `memory_recall` 恢复上下文
- 所有团队成员应能通过结构化制品加入，而不仅仅是聊天

**Trellis 原则：** 聊天历史是临时的。结构化制品是持久的。每个决策、每个计划、每个任务状态都应被捕获到超越会话生命周期的制品中。

---

**核心 Harness 规则（始终生效）：**

1. **先规范再编码** — 永远不要跳过第 1 层
2. **每次变更自动验证** — 每次文件编辑后运行完整验证序列
3. **在每个阶段边界设置检查点** — 规范完成 → 计划完成 → 实现完成 → 审查完成
4. **记忆是一等公民** — 持久化决策，而不仅仅是代码
5. **永远不要留下破损状态** — 如果验证步骤失败，先调试再继续
6. **证据先于断言** — 展示命令输出，而不仅仅说"它能工作"
7. **检查点纪律** — 如果接近会话限制，设置检查点并总结
8. **上下文预算感知** — 如果上下文低于 30%，在继续前总结/丢弃过期历史

## 模式切换 — 模式如何协同工作

十二种模式并非孤立的 — 它们形成一个自然的工作流，随着工作进展在模式间切换。

### 核心递进路径

```
Ask（探索与理解）
    ↓
Plan（设计与规划）
    ↓ [用户批准]
Spec（规范优先执行）
    ↓ [如果复杂/大型]
Harness（工程级）
```

### 常见工作流

**快速任务** — Vibe 足矣：

```
sen  → /m vibe → 任务 → 完成
```

**功能开发** — Plan → Spec：

```
/m plan
> 设计一个添加用户认证的计划
[Plan 产出详细蓝图]

/m spec
> 执行认证计划
[Spec 创建 SPEC.md，追踪变更，逐步执行]

/m tdd
> 为新的认证模块添加测试
[TDD 强制执行红-绿-重构]
```

**大型代码库重构** — ContextEng → Spec：

```
/m context
> 重构支付处理模块
[ContextEng 探索代码库，映射依赖，带影响分析执行]

/m spec
> 为重构后的支付模块添加全面测试
[Spec 追踪变更并验证]
```

**生产级功能** — Plan → Harness：

```
/m plan
> 分布式缓存系统的架构审查
[Plan 分析爆炸半径、依赖、风险]

/m harness
> 使用智能体团队编排构建分布式缓存系统
[Harness: OpenSpec → Superpowers → GSD → OMC → ECC → Trellis]
```

**调试会话** — Debug：

```
/m debug
> 修复连接池中的内存泄漏
[Debug 强制执行 复现 → 假设 → 隔离 → 修复]
```

### 会话中切换模式

可以随时使用 `/m <名称>` 切换模式。常见的会话中切换：

- **Vibe → Spec**：当 Vibe 模式中的快速实验成功且需要加固时
- **Plan → Spec**：当计划被批准且应开始执行时
- **Spec → Debug**：当规范驱动执行过程中发现 bug 时
- **ContextEng → Spec**：当探索阶段完成且开始聚焦实现时
- **任意 → Ask**：当你需要在继续之前理解某些内容时
- **Harness → Plan**：当你需要在执行中重新设计时
